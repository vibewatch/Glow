# 霁光专业风光与天文摄影审查

审查日期：2026-08-03

## 当前架构补充

本文下方保留了早期“七种摄影场景 + 三种天气工具”审查的证据链；当前产品已进一步完成任务型重构，现行结构以本节和 `weather-tools-architecture.md` 为准：

- 「每日拍摄机会」同时列出朝霞、日出、雾景、彩虹、日落、晚霞、月亮、星空、极光 9 个独立时窗；右侧议程、24 小时时间轴和地图选中方位三向联动。
- 「天气工作台」在同一个小时游标下提供云层、降雨和风况，不再把彩虹归为常规天气工具。
- 「天象事件」统一本地日月食与未来 8 个主要流星雨；远期几何和七天天气严格分离。
- 极光使用独立 NOAA SWPC Kp 接口并可单独降级；流星雨峰值按夜间范围表达，ZHR 不解释为现场必见数量。
- 地图只完整绘制当前选中的真实方向，不再同时绘制 MapLibre 与 DOM 两套重复方位线，也不从单点预报伪造区域云雨风图层。

这次重构保留了下方已经修复的逐日月亮、天文黑夜、事件对齐天气、阵风、露点差、食象语义和彩虹物理边界，并改变了用户访问这些能力的方式。

范围：从出发前筛选、机位判断、事件时刻、现场风险到复核/保存的完整摄影计划链路。审查覆盖七种摄影场景、云/雨/彩虹三种天气工具、天气与天文模型、地图方位、数据披露、响应式交互、失败恢复和可验证边界。

## 结论

霁光原有的信息架构适合“地图上先选点，再看机会”，霞光、雾景和太阳部分也已经具备专业决策所需的分层云、双模式分歧与透明贡献值。首要问题不在视觉，而在时间语义：选择未来日期后，月亮面板和地图仍展示当前月亮；地图天气条固定取当天第 12 个小时；长期食象遮掩率被复制成七个相同日分数。这会让漂亮但错时的数字直接影响出发和构图。

本次已修复这些 P0 正确性问题，并补齐一个有明确边界的星空/夜景模式、10 m 阵风和拍摄时刻现场简报。随后新增的云层、降雨和彩虹工具复用同一坐标、日期、地图、时间带和数据响应，使摄影师可以在不离开工作台的情况下从“是否有现象”继续判断“云在哪一层、雨量多大、彩虹该朝哪看”。产品现在能回答“哪一天、哪一个小时、月亮/太阳在什么方向、云风露水风险怎样”。它仍不能回答“这个机位是否被山挡住、雨幕是否正好位于反太阳方向、天空到底有多暗、银河核心是否落在前景上”，因为这些问题需要雷达/实况、地形、夜光和构图数据，不能从现有单点数值预报推断。

## 已实施的摄影决策链

1. 选点：城市搜索、浏览器定位、地图点击或拖动继续触发同一坐标的 168 小时重算。
2. 选场景与日期：霞光、雾景、太阳、月亮和星空显示七天机会；食象显示唯一长期事件，不混入七天评分。
3. 选时刻：服务端在相应事件或夜间候选小时中选出最有利时间；月亮和星空分别评分。
4. 查构图方向：日出/日落、所选夜月亮、月食食甚和日食食甚使用各自时刻的方位。
5. 查现场风险：事件小时简报给出气温、露点差、持续风、阵风、来风方向、气压和海拔。
6. 查依据与边界：三层云、降水、月光、黑夜、结露等贡献和模式分歧可见；外部数据缺口直接写在场景内。

## 后续实施计划

### 已实施 · Compact 专业决策仪表板

Compact 的目标是提高每一屏的决策信息量，而不是把文字缩回难读的 8–9px。检查器现在由统一的 `tool-panel` 网格承载：521px 及以上用两列卡位，逐小时趋势、主结论、快速指标、现场简报和方法警示保持全宽；云层剖面、贡献图和模式一致性使用半宽微型可视化并自动填充空位。520px 及以下回到单列，快速指标和现场简报仍可使用两列数据单元，避免横向挤压。

五行“名称 + 长解释 + 数值”的关键依据已替换为以零线为中心的正负发散条形图，主界面只保留因子、方向和贡献值；每个信息图标都可键盘聚焦，hover/focus 会显示完整依据，读屏仍可获得因子、解释和数值。模型一致性、三层云量和现场条件也统一使用图标、短标签、数值及微型条形图。方法边界没有被删除或藏进来源页，而是变成始终显示结论的紧凑警示条，展开后读取完整限制；数据来源继续独立折叠披露。

布局验收不以“看起来更紧”作为证据。UI 审计会确认宽屏为两列、窄手机为一列、五个贡献 hint 均可聚焦；在 1440×900 的默认霞光工作台中，云层、贡献、逐小时趋势、模式分歧和拍摄现场简报必须同时位于检查器首屏。该结构让后续雷暴、风、雪、暗空或地形工具沿用相同的主结论 / 指标 / 微型图表 / 边界披露角色，不需要再堆一套纵向卡片。

### 已实施 · 可读性与响应式密度

核心正文不再通过 8–9px 字号换取“单屏塞满”。桌面端在保留地图主导的同时，将检查器设置为 460–540px 自适应宽度；低于 1180px 时保留 420px 决策栏，900px 以下改为地图在上、详情自然纵向滚动。移动端工具轨维持单行横向切换，但点击目标、图标、标签和七天时间带同步增高。辅助来源和图表坐标可使用 9–10px，所有决策文字、警示和数据标签保持更高下限。

`expectHealthyLayout` 会在八个视口逐状态检查搜索框、工具名称、日期、面板正文、数据卡标题、方法警示、脚注和来源说明的计算字号；与溢出、裁切、无障碍和截图核对一起阻止后续密度回退。

### P1 · 机位与夜空真实性

先完成数据许可/性能原型，再进入 UI：接入夜光辐亮度并给出来源日期；用 DEM 生成相机方位上的地平线剖面；加入手动时间滑杆，让月亮、银河、方位线和现场简报随时刻同步。验收必须用山地、城市和暗空三类坐标，验证地平线遮挡、暗空差异以及跨午夜时刻。

### P1 · 可执行外拍计划

为匿名用户提供本地保存与离线快照，为登录用户提供跨设备计划；包含坐标、日期、锁定时刻、场景、风险清单、数据生成时间和“出发前复核”状态。随后再做分享链接、日历导出和通知，避免先有提醒按钮却没有可靠计划状态。

### P1 · 可靠性校准

建立用户可选的实拍结果反馈，保存视向、实际遮挡和所见现象；按地区、季节、提前时效和模式版本回测，公开样本量、可靠性曲线与 Brier Score。在此之前继续称“机会指数”，不称统计概率。

## 数据与物理边界依据

- [Open-Meteo Forecast API](https://open-meteo.com/en/docs)：现有统一天气接口及 `wind_gusts_10m` 定义；接口将小时阵风描述为前一小时最大值。
- [US Naval Observatory — Rise, Set, and Twilight Definitions](https://aa.usno.navy.mil/faq/RST_defs)：天文暮光以太阳中心位于地平线下 18° 为边界。
- [National Park Service — Light Pollution](https://www.nps.gov/subjects/nightskies/lightpollution.htm)：人造天空辉光会降低星体可见性，因此不能用天气晴朗代替暗空质量。
- [NASA Black Marble](https://blackmarble.gsfc.nasa.gov/)：夜间灯光是未来光污染层的候选数据，不代表已经完成 Bortle 等级校准或商业许可审查。
- [Copernicus DEM](https://dataspace.copernicus.eu/explore-data/data-collections/copernicus-contributing-missions/collections-description/COP-DEM)：未来地形地平线原型的候选高程源；正式接入前仍需核对覆盖、分辨率、许可和服务成本。

## 验收与证据要求

- 模型层：逐日月亮必须产生不同的计算时刻；天文黑夜、食象方位、星空和月亮极端条件有确定性测试。
- API 层：七天均包含 `moon`、`night`、`weather`、天文暮光、阵风、雨/阵雨、直射辐射和逐小时太阳几何；食象保留长期几何但不生成伪天气分数。
- 浏览器层：全部十种工具、七个日期、工具切换不导航/不重取数、方向线、现场简报、食象事件带和失败恢复在 8 个代表性视口运行；检查横向溢出、重复 ID、未命名控件、页面错误和控制台错误。
- 发布层：lint、TypeScript、37 个模型/提供方/API 测试、生产构建、22 个 Playwright 流程、14 次 Axe 扫描、依赖审计和差异检查全部通过；八个视口的 82 张截图由脚本逐项核对并人工抽查关键长/短屏状态。
